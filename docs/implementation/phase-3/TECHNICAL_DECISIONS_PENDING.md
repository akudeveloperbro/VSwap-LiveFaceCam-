# Technical Decisions Pending

**Status:** Open questions and recommendations for review. Recommendations below are not approvals. No vendor, model, runtime, paid service, region, or production architecture is selected by this document.

| ID | Decision / options | Recommendation for evaluation | Cost implications | Security / privacy implications | Blocks? |
|---|---|---|---|---|---|
| D-01 | **MVP boundary and launch claims:** image, video, live, native, WhatsApp, billing | Approve image-only batch as first inference slice; defer video/live/native/WhatsApp and payments. | Limits initial worker/storage/network spend; later capabilities need separate budgets. | Prevents users confusing preview or unsupported live UI for actual transformation. | Yes, M1–M9 scope gate. |
| D-02 | **Authentication:** managed identity (OIDC/hosted auth) vs self-hosted auth/session | Evaluate managed identity first for MVP; backend remains authoritative for authorization and ownership. Choose provider only after data terms, recovery, session/CSRF and account deletion review. | Hosted auth may have per-user/MAU fees; self-hosting costs operations and support. | Identity processor sees account data; self-hosting increases credential/session breach responsibility. | Yes, M3. |
| D-03 | **Database hosting:** managed PostgreSQL vs self-hosted PostgreSQL | Prefer managed PostgreSQL for operational simplicity, subject to approved region, encryption, backup, access and deletion terms. | Managed service recurring compute/storage/backup costs; self-hosted needs on-call, patching and recovery. | Account/job/media metadata must be regionally scoped, encrypted and access-limited. | Yes, M3. |
| D-04 | **Object storage:** provider/region/API and private bucket policy | Use private S3-compatible object storage with scoped short-lived access and deletion reconciliation; vendor/region remain open. | Storage, requests, backup and egress; image result downloads can dominate cost. | Stores face media, potentially biometric data; provider, subprocessors, region, backup retention and access logs matter. | Yes, M4. |
| D-05 | **Queue:** PostgreSQL outbox/worker poller vs managed queue vs Redis | Start with durable DB state plus transactional outbox abstraction; select a separate broker only if measured throughput/latency/delivery guarantees justify it. | DB polling may increase DB load; managed queue adds per-operation/network costs; Redis adds cluster/ops cost. | Queue payloads should carry opaque IDs, not media or credentials; delivery/log retention is sensitive. | Yes, M5. |
| D-06 | **GPU provider:** RunPod, Vast.ai, Modal, Replicate, another approved host, or CPU-only | Do not select now. Run a common, license-cleared image workload benchmark only after budget and privacy approval; GPU is conditional on approved performance target. | Compute, cold start, idle reserve, storage, egress, retries, orchestration and support. | Host isolation, region/data terms, inbound/outbound access, media scratch deletion and provider staff controls. | Blocks M6 if GPU is needed; provisioning always requires approval. |
| D-07 | **Model and weight licensing/commercial rights** | Prefer a model with explicit rights for intended hosted and commercial/non-commercial use, or obtain written rights. Audit code, weights, redistribution, derivative, output and model download terms. | Licensed alternatives may have fees, usage limits or GPU requirements; legal review has cost. | Model origin/weight downloads and output restrictions can affect user data, provider and product claims. | **Hard blocker for M6 and any real hosted inference.** |
| D-08 | **Consent and acceptable-use requirements** | Require per-job declaration/authorization of source likeness and target image; explicit remote-processing consent; revocation/reporting and synthetic disclosure policy; never infer consent from account preference. | UX, moderation, abuse response and retention systems add engineering/operations costs. | Defines lawful basis, subject rights, abusive-use response, audit collection and biometric-data treatment. | Yes, M4–M8. |
| D-09 | **Retention and deletion** | Set separate retention for originals, outputs, failed-job artifacts, worker scratch, logs/audit, backups and auth records; expose deletion pending/completed and verify object removal. | Short retention lowers storage but affects retries/support; backups and egress cost. | Deletion must cover replicas/cache/scratch/backups per stated policy; avoid durable face embeddings by default. | Yes, M4/M8/M9. |
| D-10 | **Processing region and residency** | Select region(s) only after user geography, regulatory obligations, provider availability and storage/compute co-location are known; keep data plane co-located where possible. | Regional GPU scarcity and cross-region transfer may increase cost and latency. | Determines where face data is processed, backups/subprocessors and cross-border transfer rules. | Yes, before M4 and any external processing. |
| D-11 | **Budget and resource ceilings** | Approve numeric per-user/job/session and global monthly limits, alert thresholds, shutdown behavior, max upload size, concurrency, timeout and retry budget. | Prevents unbounded spend; limits affect queue wait/UX and capacity planning. | Quotas reduce abuse and denial-of-wallet exposure; usage logs must be minimized. | Yes, before any paid resource or M5/M6 admission logic. |
| D-12 | **Vercel compatibility and deployment boundaries** | Use Vercel for the Next.js frontend if chosen, but first correct project root/framework. Host FastAPI, durable workers, and future WebRTC/GPU on a separately approved runtime suited to their lifecycle; do not assume Vercel Functions are persistent workers. | Separate platform may add hosting, network and operations cost; Vercel frontend remains subject to usage limits. | Secret boundaries and private network/media flows must avoid exposing provider endpoints or credentials. | Yes, M0/M9. Current PR check fails. |
| D-13 | **API/backend runtime and framework** | FastAPI is the leading Python candidate; compare hosting runtime and team skills. Keep inference off request handlers. | Framework low incremental cost; hosting/observability cost depends on long-lived jobs. | Strong request validation, session auth, bounded body size and secret controls required. | Yes, M2. |
| D-14 | **Tenancy and account deletion** | Begin user-scoped ownership; only add organization tenants if product requires them. Define cascade/retention exceptions before schema. | Tenant features increase schema, query, admin and support complexity. | Affects isolation, access control, analytics and deletion propagation. | Yes, M3. |
| D-15 | **Engine boundary/extraction** | Preserve current desktop modules; add a versioned adapter/interface only after import-graph and license review. | Duplicate packaging and CI until extraction is complete; possible GPU image size costs. | Separate worker identity, temp files, model provenance and restricted access are required. | Yes, M6. |
| D-16 | **Admin observability** | Collect aggregate job/worker health, latency, cost and sanitized errors; separate admin role and audit every access. Never expose media by default. | Monitoring, alerting and retention incur ongoing costs. | Logs/metrics can re-identify users; minimize identifiers and never log image bytes, embeddings, tokens, raw paths. | Yes before public/staging launch; baseline design in M2. |
| D-17 | **Payment/billing** | Exclude from MVP until plans, provider, tax/refund, entitlements and webhook authority are approved. | Processor fees, tax/compliance and chargeback work. | Payment data and entitlement manipulation risks; never trust browser price/quantity. | No for image-only MVP; blocks monetization. |
| D-18 | **Frontend framework/package manager** | Next.js App Router/React/TypeScript is the Phase 2 recommendation; isolate under `frontend/` and choose a single pinned package manager/lockfile during M0. | Build/preview usage and dependency maintenance. | Server/client boundary, CSP, browser media permissions and dependency supply-chain review. | Yes, M0/M1. |
| D-19 | **Privacy and abuse handling for model use** | Approve acceptable content, abuse-report workflow, takedown/appeal, output marking/disclosure and audit metadata before real inference. | Moderation staffing/tools and incident handling. | Prevents non-consensual likeness misuse; avoid broad retention of raw content for moderation. | Yes, M4/M6/M8. |

## Approval record template

For each item approved, record: ID; decision; alternatives rejected; evidence/date; approver/role; scope; data regions/subprocessors; cost ceiling; security/privacy controls; revisit condition. Change status only with explicit owner approval. An integration card, generated configuration, preview deployment, or this recommendation is not approval.
